Amortized Analysis: Why Vec::push is O(1)

March 5, 2026 · rust, algorithms, complexity, math

Vec::push is O(1)O(1)O(1) amortized, even though occasionally it’s O(n)O(n)O(n) (when reallocating). How?

The growth strategy

Rust’s Vec doubles capacity when full. Pushing nnn elements costs:

T(n)=n+n2+n4+⋯+1=2n=O(n)T(n) = n + \frac{n}{2} + \frac{n}{4} + \cdots + 1 = 2n = O(n)T(n)=n+2n​+4n​+⋯+1=2n=O(n)

So average per push = O(1)O(1)O(1).

Three methods

1. Aggregate

Total cost over nnn ops ≤cn\le cn≤cn, so amortized =c= c=c.

2. Accounting

Charge each push 333 credits: 111 for the push, 222 saved for future copy. When resize happens, saved credits pay for moving. Balance never negative.

3. Potential

Define potential Φ(D)=2⋅size−capacity\Phi(D) = 2 \cdot \text{size} - \text{capacity}Φ(D)=2⋅size−capacity (or similar). Amortized cost =actual+ΔΦ= \text{actual} + \Delta\Phi=actual+ΔΦ. Resizes have ΔΦ\Delta\PhiΔΦ negative enough to cancel.

Generalizing

Any structure that grows geometrically (factor >1>1>1) has O(1)O(1)O(1) amortized append. Hash maps, dynamic arrays, rope buffers all rely on this.

Caveat

Amortized bounds assume you keep the structure alive. If you push then immediately drop, you paid O(n)O(n)O(n) for nothing — but that’s fine, total work still O(n)O(n)O(n).

Rust note

Vec::with_capacity(n) avoids all reallocations if you know the size. Use it in hot paths:

let mut v = Vec::with_capacity(1024);
for i in 0..1024 { v.push(i); } // zero reallocs
